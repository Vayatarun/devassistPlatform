1What is CodeAnalyzer Pro?

CodeAnalyzer Pro is a static code analysis platform built for .NET C# developers. It automatically scans your source code and reports bugs, security vulnerabilities, performance problems, and maintainability issues — comparable to SonarQube, but running entirely on your own machine.

The tool works in three modes:

ModeDescriptionBest For
CLI ToolCommand-line scanner producing Excel, HTML, and JSON reportsDaily developer use, CI/CD pipelines, diff reviews
Web UI + APIBrowser-based dashboard with project tracking and issue managementTeam dashboards, sprint reviews, ongoing tracking
VS ExtensionRoslyn VSIX analyzer showing issues inline in Visual StudioReal-time feedback while coding
ℹ️
The CLI Tool (CodeReviewReporter) is the most feature-rich entry point and is recommended for daily use. The Web UI builds on top of it for team visibility and tracking.

3CLI Tool — CodeReviewReporter

The CLI tool analyzes C# code and generates reports. Run all commands from the E:\BackUp\TarunPractice\Analyzer1 folder.

3.1 — Scan a Folder

Scans all .cs files in a folder recursively. This is the most common mode.

dotnet run --project CodeReviewReporter -- --path "C:\Projects\MyApp"

Example with a real path:

dotnet run --project CodeReviewReporter -- --path "C:\Work\HRMS\src"
📂
The tool automatically skips bin\ and obj\ folders. Point it at your source root — it handles the rest.

3.2 — Scan Latest Git Diff

Analyzes only the files changed in the last commit. Perfect for pre-push checks or post-commit reviews.

# Run from inside your git repository
cd C:\Projects\MyApp
dotnet run --project E:\BackUp\TarunPractice\Analyzer1\CodeReviewReporter -- --git
⚠️
The --git flag requires that the current working directory is inside a git repository with at least one commit.

3.3 — Scan SVN Changes

Analyzes files changed in the current SVN working copy (uses svn diff).

dotnet run --project CodeReviewReporter -- --svn

3.4 — Scan a Saved Diff File

If you have a diff file exported from Git, SVN, TFS, or any VCS:

dotnet run --project CodeReviewReporter -- --file "C:\Diffs\sprint42-changes.diff"

To create a diff file manually:

# Git — save last commit as diff file
git diff HEAD~1..HEAD > my-changes.diff

# SVN — save working copy changes
svn diff > my-changes.diff

3.5 — Clone & Scan a Remote Repository

Clones a repo to a temporary folder, analyzes it, then cleans up automatically.

dotnet run --project CodeReviewReporter -- --repo "https://github.com/user/myrepo.git"

3.6 — Output Flags

Add these flags to any mode to generate additional report formats:

FlagOutput FileDescription
(none)CodeReviewIssues.xlsxExcel report — always generated
--htmlCodeReviewReport.htmlInteractive HTML report — open in browser
--jsonCodeReviewReport.jsonMachine-readable JSON — for CI/CD or scripts
 
# Generate all three formats
dotnet run --project CodeReviewReporter -- --path "C:\Projects\MyApp" --html --json

3.7 — Quality Gate for CI/CD

These flags make the tool return a non-zero exit code (failing the pipeline) when thresholds are exceeded.

FlagDescription
--max-critical NFail if Critical issues > N
--max-errors NFail if Error issues > N
--fail-on-gateReturn exit code 1 when any threshold is exceeded
 
# Fail pipeline if ANY critical issue is found, or more than 10 errors
dotnet run --project CodeReviewReporter -- --git --max-critical 0 --max-errors 10 --fail-on-gate

Azure DevOps Pipeline example:

- script: |
    dotnet run --project CodeReviewReporter -- --git --max-critical 0 --fail-on-gate
  displayName: 'Code Quality Gate'
  workingDirectory: $(Build.SourcesDirectory)

GitHub Actions example:

- name: Code Quality Gate
  run: dotnet run --project CodeReviewReporter -- --git --max-critical 0 --fail-on-gate
  working-directory: ./analyzer

4Web UI & API

The Web UI gives your team a shared SonarQube-style dashboard to track projects, manage issues, and configure rules from a browser.

4.1 — Starting the API

The API must be running before you open the UI. Open a terminal and run:

dotnet run --project Analyzer1.API

The API starts at https://localhost:7036. You can explore all available endpoints at:

https://localhost:7036/swagger
💡
Keep this terminal open — the API must stay running while you use the UI. Data is stored in an in-memory database and resets each time the API restarts.

4.2 — Starting the UI

Open a second terminal and run:

dotnet run --project Analyzer1.UI

Then open your browser and go to: https://localhost:7252

⚠️
If your browser shows a certificate warning, click Advanced → Proceed. This is normal for localhost HTTPS during development. Accept the dev certificate with: dotnet dev-certs https --trust

4.5 — Issues Page

Access at /issues. Investigate, filter, and triage every issue found across your projects.

Filter Bar

FilterOptions
ProjectSelect one project (required to see issues)
SeverityAll / Critical / Error / Warning / Info
CategoryAll / Security / Stability / Threading / Design / Maintainability / Readability / Efficiency / Documentation

SearchType any text — matches rule ID, message, or file name. Results update as you type.

Expanding an Issue

Click any row to expand it. The detail panel shows:

  • Issue message — the full description of the specific problem
  • Why It Matters — the real-world risk or impact
  • Remediation — general guidance for this type of problem
  • Suggested Fix — specific action to take on this exact instance
  • Bad Code (red) — an example of the problematic pattern
  • Good Code (green) — the correct way to write it
  • Status buttons — change the issue status

Issue Status Workflow

StatusMeaningWhen to Use
OpenActive issue needing attentionDefault state after scan
ResolvedFixed in source codeAfter you fix the issue
Won't FixAcknowledged but intentionalWhen the pattern is deliberate by design
False PositiveRule misfiredWhen the rule is wrong about this specific case
💡
Only Open issues count toward the Quality Gate. Marking issues as Resolved, Won't Fix, or False Positive excludes them from future gate checks.

4.6 — Rules Page

Access at /rules. View and configure all 50+ analysis rules.

Category Chips

Click a chip at the top to filter the rules table to one category. Click again to deselect.

Expanding a Rule

Click any row to see the full description, remediation guidance, and severity override control.

Disabling a Rule

Toggle the switch in the Enabled column. Disabled rules are ignored in future scans. Useful when a rule produces too many false positives for your specific codebase.

Overriding Severity

Expand a rule and use the Override Severity dropdown to change a rule's severity. For example, change MAIN001 Deep Nesting from Warning to Error if your team treats it as a serious issue.

Example Issue — Expanded

https://localhost:7252/issues
Critical SEC001 SQL Injection UserRepository.cs : 42 ▲
Why It Matters
An attacker can manipulate the SQL query to access, modify, or delete any data in the database.
Suggested Fix
Replace string concatenation with parameterized queries using SqlParameter.
⯈ Bad Code
var sql = "SELECT * FROM Users WHERE id = " + userId;
✓ Good Code
cmd.CommandText = "SELECT * FROM Users WHERE id = @id";
cmd.Parameters.AddWithValue("@id", userId);

7Common Workflows

📅 Daily Developer Check

After committing, scan your recent changes and review the HTML report before pushing.

🔍 Pre-Merge Code Review

Generate a diff from a feature branch and share the HTML report with reviewers.

🛡 CI/CD Quality Gate

Automatically block merges that introduce Critical issues or exceed error thresholds.

📊 Team Dashboard

Run the Web UI so the whole team can see project health and track issue resolution.

Workflow 1 — Daily Developer Check

# After committing your changes:
cd C:\Projects\MyApp
dotnet run --project E:\BackUp\TarunPractice\Analyzer1\CodeReviewReporter -- --git --html

# Open the report:
start CodeReviewReport.html

Workflow 2 — Pre-Merge Code Review

# On your feature branch:
git diff main...HEAD > pr-review.diff

# Analyze the diff:
dotnet run --project CodeReviewReporter -- --file pr-review.diff --html

# Share CodeReviewReport.html with the reviewer via email or Teams

Workflow 3 — CI/CD Quality Gate

# Azure DevOps
- script: dotnet run --project CodeReviewReporter -- --git --max-critical 0 --max-errors 5 --fail-on-gate
  displayName: 'Code Quality Gate'

# GitHub Actions
- name: Quality Gate
  run: dotnet run --project CodeReviewReporter -- --git --max-critical 0 --fail-on-gate

Workflow 4 — Team Dashboard (Web UI)

# Terminal 1 — Start API
dotnet run --project Analyzer1.API

# Terminal 2 — Start UI
dotnet run --project Analyzer1.UI

# Browser → https://localhost:7252
# 1. Go to Projects → Add Project → enter your project name + path
# 2. Click "Scan" on the project card
# 3. Dashboard automatically shows results
# 4. Share the URL with your team (all on the same network)

Workflow 5 — Weekly Audit Report

# Generate all formats for the full codebase
dotnet run --project CodeReviewReporter -- --path "C:\Projects\HRMS" --html --json

# CodeReviewIssues.xlsx — paste into sprint review deck
# CodeReviewReport.html — share with tech lead
# CodeReviewReport.json — import into JIRA or Confluence via script
💡
Pro Tips:
  • Start by fixing Critical and Error issues first — they carry the highest risk and the most tech debt.
  • Use Won't Fix status in the UI for intentional patterns — they stop cluttering your dashboard.
  • Use --git mode rather than scanning the whole folder in CI — it's faster and focuses on what changed.
  • If a rule fires too much on your codebase, disable it on the Rules page rather than ignoring the results.
